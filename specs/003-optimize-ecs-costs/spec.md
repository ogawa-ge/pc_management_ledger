# Feature Specification: NAT GatewayとECS稼働数のコスト最適化

**Feature Branch**: `003-optimize-ecs-costs`  
**Created**: 2026-08-28  
**Status**: Draft  
**Input**: User description: "Issue #16: NAT GatewayとECS稼働数のコスト最適化を検討する"

## Clarifications

### Session 2026-09-02

- Q: 起動完了後、停止中に受け付けた元操作をどのように扱うか？ → A: システムが元操作を自動再送し、同一要求は1回だけ処理する。
- Q: 停止処理の直前または実行中に新しい操作を受けた場合、どの優先ルールを採用するか？ → A: 停止を可能なら中止して稼働を維持し、中止不能なら停止完了後に自動再起動して元操作を1回だけ処理する。
- Q: バックエンド処理を必要とする操作が処理中の場合、自動停止をどのように扱うか？ → A: 操作の受付時と成功完了時にアクティビティ時刻を更新し、処理中は自動停止しない。
- Q: 停止状態からの自動再送に関する受け入れ試験で、必須とするPC管理操作の範囲はどれか？ → A: 参照系操作1種、PC登録、PC返却を含め、状態変更操作が重複しないことを確認する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 低コスト構成の採用判断 (Priority: P1)

システム運用責任者は、現在のネットワーク構成と低コストな代替案について、必要な外部・AWSサービスへの通信可否、固定費、利用量に応じた費用、運用上の制約を同じ条件で比較し、月額数百円〜数千円という目標に最も適した構成を採用できる。

**Why this priority**: 常時発生するネットワーク固定費が小規模利用のコスト目標を妨げる可能性があり、通信を失わずに必要性と代替案を判断することがIssue #16の中心だから。

**Independent Test**: 現行案と1つ以上の代替案について、Gemini API、DynamoDB、ECR、CloudWatch Logsへの通信、月額概算、利点、欠点、採否が記録され、第三者が同じ前提で判断を追跡できることを確認する。

**Acceptance Scenarios**:

1. **Given** 小規模利用を想定した共通の利用条件が定義されている, **When** 運用責任者が現行案と代替案を比較する, **Then** 各案の固定費、利用量連動費、必要な通信の可否、運用上の制約が同じ月次条件で示される
2. **Given** 各候補の比較結果が揃っている, **When** 運用責任者が採用構成を決定する, **Then** 採用案、却下案、判断理由、月額概算、見直し条件が記録される
3. **Given** 採用候補の環境が検証可能である, **When** 必要な通信を確認する, **Then** Gemini APIの呼び出し、DynamoDBの読み書き、ECRからのタスク起動、CloudWatch Logsへのログ出力がすべて成功する

---

### User Story 2 - 停止状態からの自動利用再開 (Priority: P1)

利用者は、バックエンド処理が停止しているときにPC管理機能へアクセスしても、起動中であることを理解でき、手動の運用依頼やページの繰り返し更新をせずに、起動完了後に要求した操作をシステムの自動再送によって完了できる。

**Why this priority**: 初期稼働数を0にして待機費用を抑えるには、コールドスタートを利用不能や障害に見せない起動・再試行体験が不可欠だから。

**Independent Test**: バックエンド処理が停止した状態から参照系操作1種、PC登録、PC返却を開始し、自動起動、起動中表示、自動再送、正常完了までを利用者操作の喪失なく確認する。PC登録とPC返却は、再送または競合があっても業務上の結果が重複しないことを確認する。

**Acceptance Scenarios**:

1. **Given** バックエンド処理が停止している, **When** 利用者がバックエンド処理を必要とする操作を開始する, **Then** システムは起動を開始し、利用者に一時的な起動待ちであることを表示する
2. **Given** バックエンド処理が起動途中である, **When** 利用者が画面で待機する, **Then** システムは過剰な起動要求を発生させずに再試行し、利用可能になった後に元の操作を自動再送して1回だけ処理する
3. **Given** 起動または再試行が許容待ち時間内に完了しない, **When** 待機上限に達する, **Then** システムは障害と区別できる案内と、安全に再試行する手段を利用者へ示す

---

### User Story 3 - 未使用時の自動スリープ (Priority: P2)

システム運用責任者は、利用者の有効な操作が2時間ないときにバックエンド処理が自動停止し、利用中の操作がある間は停止しないことを確認できる。

**Why this priority**: 初期停止だけでなく、利用後に確実に停止へ戻ることが継続的なコスト削減に必要だから。

**Independent Test**: 最終アクティビティ時刻を境界値の前後に設定し、停止判定を実行して、2時間未満では稼働を維持し、2時間以上では停止することを確認する。

**Acceptance Scenarios**:

1. **Given** バックエンド処理が稼働中で最終有効アクティビティから2時間未満である, **When** 定期停止判定が行われる, **Then** 稼働状態が維持される
2. **Given** バックエンド処理が稼働中で最終有効アクティビティから2時間以上経過している, **When** 定期停止判定が行われる, **Then** バックエンド処理が停止状態へ移行する
3. **Given** 複数利用者が操作している, **When** いずれかの有効な操作が記録される, **Then** 最終アクティビティが更新され、その操作から2時間未満は自動停止しない
4. **Given** 自動停止の直前または停止処理中である, **When** 新しい有効な操作が到着する, **Then** システムは可能なら停止を中止して稼働を維持し、中止できない場合は停止完了後に自動再起動して元操作を1回だけ処理する
5. **Given** バックエンド処理を必要とする操作が実行中である, **When** 定期停止判定が行われる, **Then** システムは処理中の操作が終了するまで自動停止せず、成功完了時刻からアイドル時間を計測する

---

### User Story 4 - 最適化効果の確認 (Priority: P3)

システム運用責任者は、採用構成の導入後に、実際の稼働時間と請求傾向が事前の月額概算から大きく外れていないかを確認し、必要に応じて構成を見直せる。

**Why this priority**: 見積りだけでなく実績を確認することで、利用パターンや価格前提のずれによる想定外の費用を早期に発見できるから。

**Independent Test**: 導入後の連続30日または利用可能な最初の請求期間について、主要費用項目の実績と見積りを比較し、差異と対応判断が記録されることを確認する。

**Acceptance Scenarios**:

1. **Given** 採用構成が運用され費用実績が取得可能である, **When** 運用責任者が見積りと実績を比較する, **Then** 主要費用項目ごとの差額、差率、原因候補が確認できる
2. **Given** 実績が目標上限または見積り許容差を超えている, **When** 運用責任者が結果を確認する, **Then** 再評価の要否と次の対応が記録される

### Edge Cases

- 停止直前または停止処理中に新しい利用者操作が到着した場合、可能なら停止を中止して稼働を維持し、中止できない段階なら停止完了後に自動再起動して元操作を1回だけ処理する。
- 複数の利用者が停止状態へ同時にアクセスした場合、起動処理を重複させず、各利用者に一貫した起動中状態を示す。
- 起動したタスクに到達可能なアドレスがまだ割り当てられていない場合、準備完了と誤判定せず再試行を継続する。
- アクティビティ記録の欠落、未来日時、不正形式がある場合、安全側の判断として稼働中タスクを直ちに停止せず、異常を運用者が確認できるようにする。
- Gemini APIまたはいずれかの必要なAWSサービスに一時的に到達できない場合、ネットワーク構成の恒常的な不備と一時障害を区別して検証結果を記録する。
- ECRからのイメージ取得が必要なのは新規タスク起動時であるため、稼働中の疎通確認だけで通信維持を合格としない。
- 月の途中で価格、為替、利用時間が変わる場合、見積りの基準日、通貨、リージョン、利用量を固定して比較可能性を保つ。
- 月額概算が目標上限を超える候補しかない場合、通信や利用継続性を犠牲にして採用せず、未達理由と追加の代替案を記録する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 評価結果 MUST 現行のネットワーク構成と、NAT Gatewayを常設しない案を少なくとも1案含める。
- **FR-002**: 評価結果 MUST 各候補について、Gemini API、DynamoDB、ECR、CloudWatch Logsへの必要な送信通信が可能かを個別に示す。
- **FR-003**: 評価結果 MUST 各候補の固定費、利用量に応じた費用、データ通信費、および運用上の制約を共通の月次利用条件で比較する。
- **FR-004**: 評価結果 MUST 価格の基準日、対象リージョン、通貨、為替前提、月間利用時間、通信量、および見積りに含めた費用項目を記録する。
- **FR-005**: 運用責任者 MUST 比較結果に基づいて採用構成を1つ決定し、採用理由、却下案の理由、既知のリスク、見直し条件を記録できる。
- **FR-006**: 採用構成 MUST 新規タスク起動を含む検証において、Gemini API、DynamoDB、ECR、CloudWatch Logsへの必要な通信を維持する。
- **FR-007**: 採用する初期稼働方針 MUST デプロイ完了直後および通常の未使用待機時にバックエンド処理を停止状態とし、常時タスク費用を発生させない。
- **FR-008**: システム MUST 停止状態で対象操作を受けたとき、自動的にバックエンド処理の起動を要求する。
- **FR-009**: システム MUST 起動処理中であることを利用者に明示し、推奨待機時間に基づいて自動再試行する。
- **FR-010**: システム MUST 同時アクセスまたは再試行による重複した起動要求を抑止する。
- **FR-010a**: システム MUST 起動完了後に停止中に受け付けた元の操作を自動再送し、同一要求の再送または競合が発生しても業務上の処理を1回だけ成立させる。
- **FR-011**: システム MUST 起動待ちが3分を超えた場合、自動再試行を終了し、要求が未完了であることと利用者が安全に再試行できる方法を示す。
- **FR-012**: システム MUST バックエンド処理を必要とする利用者操作について、受付時と成功完了時に停止判定用のアクティビティ時刻を更新し、処理中であることを識別可能にする。
- **FR-012a**: システム MUST バックエンド処理を必要とする操作が処理中である間は自動停止せず、成功完了時刻からアイドル時間を計測する。
- **FR-013**: システム MUST 最終有効アクティビティから2時間未満は稼働中のバックエンド処理を自動停止しない。
- **FR-014**: システム MUST 最終有効アクティビティから2時間以上経過した稼働中のバックエンド処理を、定期判定により停止状態へ移行する。
- **FR-014a**: システム MUST 自動停止の直前または停止処理中に新しい有効な操作を受けた場合、可能なら停止を中止して稼働を維持し、中止できない場合は停止完了後に自動再起動して元操作を1回だけ処理する。
- **FR-015**: システム MUST アクティビティ記録が欠落または不正な場合に稼働中処理を即時停止せず、運用者が異常を識別できる記録を残す。
- **FR-016**: 検証記録 MUST 参照系操作1種、PC登録、PC返却のそれぞれについて、初期停止、自動起動、起動中表示、自動再試行、元操作の自動再送、重複のない処理成功、2時間アイドル後の停止という一連の流れを再現する手順と結果を含む。
- **FR-017**: 運用責任者 MUST 導入後30日または最初の完全な請求期間について、見積りと実績を主要費用項目ごとに比較し、目標超過または20%を超える差異の対応判断を記録できる。
- **FR-018**: 最適化 MUST 既存の認証・認可、PC管理、PC返却、Geminiによるスペック抽出の業務上の結果を変更しない。

### Key Entities

- **構成候補**: 比較対象となるネットワークおよびバックエンド稼働方針。通信可否、費用区分、利点、制約、リスク、採否を持つ。
- **コスト見積り**: 特定の基準日、リージョン、通貨、利用条件における候補ごとの月額概算。固定費、利用量連動費、通信費、合計を含む。
- **採用判断**: 選択した構成、判断理由、却下理由、既知のリスク、見直し条件を関連付けた意思決定記録。
- **バックエンド稼働状態**: 停止中、起動中、稼働中、停止処理中、起動失敗を区別する利用・運用上の状態。
- **最終有効アクティビティ**: 自動停止の基準となる、バックエンド処理を必要とした直近操作の受付時刻または成功完了時刻。処理中状態と組み合わせて停止可否を判断する。
- **検証記録**: 必要な通信、自動起動、再試行、自動停止について、前提、実施日時、結果、失敗理由を追跡する記録。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 現行案と1つ以上の代替案の100%について、4つの必要な通信先、月額概算、利点、制約、リスク、採否が記録される。
- **SC-002**: 採用構成の月額概算が、定義した小規模利用条件において月額3,000円以下となるか、超過する場合は理由と追加対応が明示される。
- **SC-003**: 採用構成で実施する新規タスク起動を含む通信試験において、Gemini API、DynamoDB、ECR、CloudWatch Logsの4項目すべてが成功する。
- **SC-004**: 停止状態から開始する参照系操作1種、PC登録、PC返却の受け入れ試験を各5回実施し、全15回で起動中表示、自動再試行、元操作の自動再送、および最終的な操作成功を3分以内に完了する。PC登録とPC返却の全10回で業務上の結果が重複しない。
- **SC-005**: 同時に10件の起動要求を行う試験で、バックエンド処理の起動は1回に集約され、10件すべてが起動中または利用可能の一貫した状態を受け取る。
- **SC-006**: 2時間の境界前後を含む停止判定試験の100%で、2時間未満の有効アクティビティがある場合は稼働を維持し、2時間以上ない場合は次回の定期判定から15分以内に停止する。
- **SC-007**: デプロイ完了直後および自動停止完了後の確認で、バックエンドの稼働タスク数が0となる。
- **SC-008**: 導入後30日または最初の完全な請求期間について、主要費用項目の実績と見積りの差率が記録され、合計実績が目標上限または見積りを20%超過した場合は再評価判断が残される。

## Assumptions

- 対象は20〜30名程度が貸出・返却など特定のタイミングで利用する小規模環境であり、常時高トラフィックは想定しない。
- コスト目標の判定上限は、憲章の「月額数百円〜数千円」を検証可能にするため月額3,000円とする。業務上の必須通信や安全性を犠牲にして上限を達成することは認めない。
- 自動スリープのアイドル時間は既存方針どおり2時間とし、判定は15分以内の間隔で行われる前提とする。
- 停止状態からの起動では通常時より待ち時間が長くなることを許容するが、利用者には起動中と障害を区別して案内する。
- 月額比較はAWS Cost Explorerまたは請求実績と、AWS Pricing Calculatorまたは同等の公式価格情報を根拠とし、基準日と見積り条件を残す。
- 必要な通信先はIssue #16に明記されたGemini API、DynamoDB、ECR、CloudWatch Logsを最低範囲とし、検証中に別の必須依存先が判明した場合は比較と通信試験へ追加する。
- 既存のフロントエンド、認証、PC管理データ、および外部APIの契約は利用可能であり、本機能では業務データモデルを変更しない。

## Out of Scope

- PC管理、PC返却、ユーザー管理、認証、Geminiスペック抽出そのものの機能変更。
- 月額目標と必要な通信の両立に不要な全面的アーキテクチャ刷新。
- AWS以外のクラウドへの移行、または外部APIの置き換え。
- 過去の請求額の返金、会計処理、予算承認フローの変更。
- 将来の大規模・常時高負荷利用を前提とした容量設計。
