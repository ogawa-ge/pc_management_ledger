# Feature Specification: ログイン方式のGoogle Workspaceへの変更

**Feature Branch**: `004-google-workspace-login`

**Created**: 2026-10-16

**Status**: Draft

**Input**: User description: "GitHub Issue #19 ログインをteamsからgoogle workspaceに変更"

## 背景

現在のPC管理台帳は、Microsoftアカウント（Teams / Microsoft 365 の社内アカウント）によるシングルサインオンでログインしている（`specs/001-pc-management/spec.md` FR-001）。社内の利用アカウントがGoogle Workspaceへ移行するため、ログイン手段をGoogle Workspaceの社内アカウント（`@genuine-pt.jp`）に切り替える。

既存のMicrosoftアカウントのユーザーとの照合・引き継ぎは行わず、Google Workspaceアカウントを完全に新しいアカウントとして扱う。権限管理（管理者 / 一般ユーザー）はこれまでどおり本システム内で行う。

## Clarifications

### Session 2026-10-16

- Q: 既存ユーザー（Microsoftアカウント）とGoogle Workspaceアカウントの照合は必要か？ → A: 不要。完全に新しいアカウントに切り替える。
- Q: ログインを許可するアカウントの範囲は？ → A: `@genuine-pt.jp` のアカウントのみ許可し、それ以外はすべて除外する。

### Session 2026-10-19

- Q: 切り替え後、Microsoftアカウント時代の旧ユーザーは、ユーザー一覧やPC所有者のプルダウンにどう表示するか？ → A: 旧ユーザーのデータは削除する（ユーザー情報の構成自体を作り直す前提）。
- Q: 旧ユーザーを削除するとき、そのユーザーとつながっているPCの所有者情報、返却記録、利用履歴はどう扱うか？ → A: PC情報も含めてすべて削除し、登録し直す。開発途中で本番として使っているデータは存在しない。
- Q: データを空にして切り替えた直後、最初の管理者はどうやって決めるか？ → A: 従来どおり、本人が初回ログインした後に、データベースを直接操作して手動で管理者にする。
- Q: `@genuine-pt.jp` 以外のアカウントでログインが拒否されたとき、その試行を記録に残すか？ → A: サーバーのログに日時と拒否したメールアドレスを残す（画面での閲覧機能は作らない）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Google Workspaceアカウントでのログイン (Priority: P1)

社員は、ログイン画面で「Googleアカウントでログイン」を選び、`@genuine-pt.jp` のGoogle Workspaceアカウントで認証して本システムを利用開始できる。ログイン後は、本システムに登録された権限（管理者 / 一般ユーザー）に応じた画面が表示される。

**Why this priority**: ログインは全機能の前提であり、移行後にMicrosoftアカウントが使えなくなると誰もシステムを利用できなくなるため。

**Independent Test**: `@genuine-pt.jp` のアカウントでログインし、権限に応じたPC一覧画面が表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** ログイン画面を開いている, **When** `@genuine-pt.jp` のアカウントでログインする, **Then** ログインに成功し、権限に応じたPC一覧画面が表示される
2. **Given** `@genuine-pt.jp` のアカウントで初めてログインする, **When** ログインが完了する, **Then** 一般ユーザー権限の新規ユーザーとして登録される
3. **Given** ログインしていない状態, **When** 保護されたページにアクセスする, **Then** ログイン画面にリダイレクトされる
4. **Given** ログイン画面を開いている, **When** 画面を確認する, **Then** Microsoftアカウントでのログイン手段は表示されず、Googleアカウントでのログイン手段のみが表示される
5. **Given** ログイン済みの状態, **When** ログアウトする, **Then** セッションが終了し、ログイン画面に戻る

---

### User Story 2 - `@genuine-pt.jp` 以外のアカウントの拒否 (Priority: P1)

`@genuine-pt.jp` 以外のGoogleアカウント（個人のGmailアカウントや他社のGoogle Workspaceアカウントなど）では、本システムにログインできない。

**Why this priority**: 社内資産情報を扱うため、社外の人がログインできると情報漏えいにつながる。セキュリティ上、US1と同時に必須となる。

**Independent Test**: 個人のGmailアカウントでログインを試み、拒否されてエラーメッセージが表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** ログイン画面を開いている, **When** 個人のGmailアカウント（`@gmail.com`）でログインを試みる, **Then** ログインは拒否され、「会社のGoogleアカウント（@genuine-pt.jp）でログインしてください」という趣旨のメッセージが表示される
2. **Given** ログイン画面を開いている, **When** 他組織のGoogle Workspaceアカウントでログインを試みる, **Then** ログインは拒否され、同様のメッセージが表示される
3. **Given** `@genuine-pt.jp` 以外のアカウントでログインを試みた, **When** ログインが拒否される, **Then** そのアカウントはユーザーとして登録されない

---

### Edge Cases

- `genuine-pt.jp` に似た別ドメイン（例: `@genuine-pt.jp.example.com`、`@sub.genuine-pt.jp`、`@genuine-pt.jpx`）は許可せず、ドメインが `genuine-pt.jp` と完全に一致する場合のみ許可する。大文字・小文字の違いは同一とみなす。
- Google側でメールアドレスの確認が済んでいないアカウントは許可しない。
- Google側の認証サービスが一時的に利用できない場合、ログイン画面に「しばらくしてから再度お試しください」という趣旨のメッセージを表示し、システム内部のエラー詳細は表示しない。
- ユーザーがGoogleのアカウント選択画面・同意画面でキャンセルした場合、ログイン画面に戻り、エラーではなく通常の状態として扱う。
- Google Workspace組織から削除（退職など）されたアカウントは、次回のログイン時点でログインできなくなる。
- 移行前にMicrosoftアカウントで発行されたログインセッションは、切り替え後に無効となり、再ログインを求められる。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、Google Workspaceアカウントを用いたシングルサインオンによるログイン機能を提供しなければならない。
- **FR-002**: システムは、メールアドレスのドメインが `genuine-pt.jp` と完全に一致するアカウントのみログインを許可し、それ以外のアカウント（個人のGmail、他組織のアカウント、類似ドメイン、サブドメイン）はすべて拒否しなければならない。
- **FR-003**: 許可ドメインはソースコードに直接書き込まず、設定値（環境変数）で指定しなければならない。認証に必要な接続情報（クライアントID・シークレットなど）も環境変数またはシークレット管理の仕組みで管理し、リポジトリに含めてはならない。
- **FR-004**: ドメインの判定は、ログイン画面での表示や入力補助だけに頼らず、サーバー側で認証結果に対して必ず行わなければならない。
- **FR-005**: システムは、Microsoftアカウントによるログイン手段を廃止し、ログイン画面およびシステム全体から除去しなければならない。
- **FR-006**: 既存のMicrosoftアカウントのユーザーとの照合・データ引き継ぎは行わない。Google Workspaceアカウントでの初回ログイン時は、一般ユーザー権限の新規ユーザーとして登録しなければならない。
- **FR-006a**: 既存のデータ（ユーザー、PC、返却記録、利用履歴）は引き継がず、空の状態から運用を始めなければならない。データの構成は、必要に応じてGoogle Workspaceアカウント前提で作り直す。切り替え後、旧ユーザーや旧データはどの画面にも表示されてはならない。
- **FR-007**: 権限（管理者 / 一般ユーザー）は、従来どおり本システム内の権限情報で管理し、Google Workspace側の権限やグループは利用してはならない（`specs/001-pc-management/spec.md` FR-002 の方針を維持する）。
- **FR-008**: ログイン失敗時（許可外ドメイン、認証サービス障害など）には、原因に応じた利用者向けメッセージを日本語で表示し、内部のエラー詳細は表示してはならない。
- **FR-009**: ログイン・ログアウトの挙動（未ログイン時のリダイレクト、ログアウト後のログイン画面表示）は、従来のMicrosoftアカウントログイン時と同等でなければならない。
- **FR-010**: 認証処理は、従来どおり常時稼働の軽量な実行環境で行い、スリープ運用のバックエンド処理基盤を起動させてはならない（Constitution Layer 3「Hybrid Responsibility」「Cost-Awareness」を維持する）。
- **FR-011**: 画面上の文言（「Microsoftアカウントでログイン」など）と、用語集（`docs/ubiquitous-language.md` の User の定義）を、Google Workspaceアカウントに合わせて更新しなければならない。
- **FR-012**: 許可外ドメインのためにログインを拒否したときは、サーバー側の運用ログに、日時と拒否したメールアドレスを記録しなければならない。記録を画面で閲覧する機能は設けない。

### Key Entities *(include if feature involves data)*

- **User**: システムを利用する社員。本機能以降は `@genuine-pt.jp` のGoogle Workspaceアカウントで識別する。氏名、メールアドレス、権限（管理者 / 一般ユーザー）を持つ。Microsoftアカウント時代のユーザーは引き継がず、ユーザー情報の構成は必要に応じてGoogle Workspaceアカウント前提で作り直す。
- **許可ドメイン**: ログインを許可するメールアドレスのドメイン（`genuine-pt.jp`）。設定値として管理し、データとしては保持しない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 社員は `@genuine-pt.jp` のアカウントを使用して、1分以内にログインを完了できる。
- **SC-002**: `@genuine-pt.jp` 以外のアカウント（個人のGmail、他組織、類似ドメイン、サブドメイン）によるログイン試行は、100%拒否される。
- **SC-003**: 切り替え後、Microsoftアカウントでログインできる経路が画面上・システム上に一切残っていない。
- **SC-004**: 切り替えによって、ログインのために常時稼働していない処理基盤が起動されることはなく、月額インフラコストが増加しない。

## Assumptions

- 社員全員が `@genuine-pt.jp` のGoogle Workspaceアカウントをすでに保有しており、切り替え日以降はそのアカウントで業務を行う。
- 切り替えは一括で行い、MicrosoftアカウントとGoogle Workspaceアカウントを併用する期間は設けない。
- 本システムは開発途中であり、本番として使っているデータは存在しない。そのため既存データを引き継がず、必要に応じてデータの構成から作り直しても業務への影響はない。
- 切り替え後のPC情報の登録（Excelで管理しているPCの移行を含む）は、既存の登録機能や別途のデータ移行で行い、本機能の範囲外とする。
- 切り替え直後に最初の管理者となるユーザーは、そのユーザーが初回ログインした後、従来どおりデータベースを直接操作して手動で権限を設定する。管理者を自動で決める仕組み（設定値での指定、最初のログイン者を管理者にするなど）は設けない。
- Google Workspace側の設定（本システムをGoogleの認証連携先として登録する作業）は、情報システム担当が別途実施でき、開発チームは必要な設定値を受け取れる。
- Google Workspaceのグループ等との権限連携は、本機能の範囲外とする。
- 対象はWebブラウザからのログインのみとし、モバイルアプリ等は範囲外とする。
