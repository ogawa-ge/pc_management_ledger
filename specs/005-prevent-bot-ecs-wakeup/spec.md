# Feature Specification: ボットアクセスによる不要起動防止と自動停止の確実化

**Feature Branch**: `005-prevent-bot-ecs-wakeup`

**Created**: 2026-11-06

**Status**: Completed

**Input**: User description: "GitHub Issue #27: fix: ボット等の非APIパスアクセスによるECS不要起動とlastActivityAt未設定による自動停止スキップの防止"

## 背景と課題

本システムは、徹底したコスト最適化のため、利用者がいないアイドル時は重量級のバックエンド処理基盤をスリープ状態（タスク数0）に維持し、利用者が画面を開いた際にオンデマンドで自動起動する仕組みを採用している。

しかし実環境検証において、インターネット上の検索クローラーやスキャンボットが `/robots.txt` などの非業務パスに単発アクセスした際、以下の重大な問題が発生することが判明した：
1. **不要な起動の発生**: 業務外のパスへの単発アクセスにもかかわらず、バックエンド処理基盤の自動起動がトリガーされてしまう。
2. **自動スリープの永久スキップ（課金継続）**: ボットや早期離脱ユーザーのように、初回要求の起動受付（503通知）後に後続の業務要求を送信しない場合、最終活動時刻が記録されず起動中状態のまま孤立する。その結果、定期アイドル監視パトロールが「異常記録（時刻未設定）」と判定して安全装置（フェイルオープン）により停止処理を見送り続け、次回人間がアクセスするまで不要なコンテナ稼働課金が発生し続けてしまう。

本機能では、非業務パスへのアクセスによる起動を完全に遮断し、万一の単発起動時にも規定時間経過後に確実に自動停止するよう安全対策を強化する。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 非業務パスアクセス時の不要起動防止 (Priority: P1) 🎯 MVP

外部の検索ボット、クローラー、スキャナーなどが業務外のパス（`/robots.txt`, `/favicon.ico` など）へアクセスした際、システムはバックエンド処理基盤の起動処理を行わずに即座に対象外（404 Not Found）として応答を完了する。これにより、無駄なコンテナ起動や課金の発生を未然に防止する。

**Why this priority**: インターネット公開エンドポイントにおいて日常的に発生するボット巡回によるインフラ費用の浪費を根本から防止するため、最優先で必要。

**Independent Test**: バックエンド処理基盤が停止している状態で `/robots.txt` などの非業務パスへアクセスし、バックエンドが起動されず即座に対象外応答が返ることを確認する。

**Acceptance Scenarios**:

1. **Given** バックエンド処理基盤が停止している, **When** クローラーが `/robots.txt` へアクセスする, **Then** バックエンド処理基盤は起動されず、即座に 404 Not Found が返却される
2. **Given** バックエンド処理基盤が停止している, **When** ブラウザ等が `/favicon.ico` などの未定義パスへアクセスする, **Then** バックエンド処理基盤は起動されず、即座に 404 Not Found が返却される
3. **Given** バックエンド処理基盤が稼働している, **When** 未定義パスへアクセスする, **Then** バックエンド処理基盤の活動時刻は更新されず、即座に 404 Not Found が返却される

---

### User Story 2 - クライアント早期離脱・単発アクセス時の確実な自動停止 (Priority: P1) 🎯 MVP

利用者が起動待機中にブラウザを閉じた場合や、何らかの理由で単発の起動要求後に後続の通信が一切行われなかった場合でも、システムは起動要求時刻を基準としてアイドル判定を行い、規定アイドル時間（2時間）経過後の定期パトロールで確実にスリープ状態（タスク数0）へ自動停止させる。

**Why this priority**: 初回アクセス後に通信が途絶えた場合でもコンテナが放置されず、夜間や休日の課金をゼロに抑えるために必須。

**Independent Test**: 停止状態から起動要求を1回だけ発行し、後続の業務要求を一切送らずに2時間アイドルを模した状態で監視パトロールを実行した際、正常に自動停止（タスク数0）へ遷移することを確認する。

**Acceptance Scenarios**:

1. **Given** バックエンド処理基盤が停止している, **When** 初回の起動要求が発生し後続の業務通信が0件のまま規定アイドル時間（2時間）が経過する, **Then** 次回の定期監視パトロールでバックエンド処理基盤が確実にスリープ状態（タスク数0）へ自動停止される
2. **Given** バックエンド処理基盤が起動要求を受け付けた, **When** 起動処理を開始する, **Then** システム活動記録に初期活動時刻として現在時刻が正しく記録される
3. **Given** 起動中状態でクライアントが離脱した, **When** 定期監視パトロールが実行される, **Then** 異常記録としてスキップされることなく、起動要求からの経過時間に基づいて正しく停止判定が行われる

---

### User Story 3 - 正規業務API利用時の既存オンデマンド起動とスリープ運用の維持 (Priority: P2)

正規の利用者がPC管理台帳の画面を操作する際、停止中であればこれまでどおりオンデマンドで自動起動して業務を継続でき、業務終了後は最後の操作から規定アイドル時間経過後に自動スリープする既存の運用が正常に維持される。

**Why this priority**: コスト抑止の改善によって正規利用者の利便性や既存の自動起動・停止機能が損なわれないことを保証するため。

**Independent Test**: 正規のAPI（PC一覧取得など）へアクセスし、停止状態からの自動起動・画面表示・最終活動時刻の更新、および利用停止後の自動スリープが正常に行われることを確認する。

**Acceptance Scenarios**:

1. **Given** バックエンド処理基盤が停止している, **When** 利用者が正規の業務API（`/api/pcs` など）へアクセスする, **Then** 従来どおり起動がトリガーされ、起動完了後に正常に応答が返却される
2. **Given** バックエンド処理基盤が稼働している, **When** 利用者が業務APIを操作する, **Then** 正常応答時に最終活動時刻が最新時刻に更新される
3. **Given** 業務操作が終了し最後の操作から規定アイドル時間が経過した, **When** 定期監視パトロールが実行される, **Then** バックエンド処理基盤が正常にスリープ状態へ遷移する

---

### Edge Cases

- **非業務パスへの大量連続アクセス**: クローラーが複数の未定義パスへ連続アクセスした場合でも、すべて即座に404を返し、起動処理が一切呼び出されないこと。
- **起動中における正規APIの再送**: 起動処理中に同一または別の正規API要求が到着した場合、既存の起動プロセスを集約して二重起動を行わず、起動完了後に正しく処理されること。
- **停止処理と新規正規API要求の競合**: 定期パトロールによる停止処理が開始された瞬間に新たな正規API要求が到着した場合、停止処理を安全に中断または再起動して新規要求を正常に処理すること。
- **起動失敗時のハンドリング**: バックエンド処理基盤の起動処理自体がインフラ障害等で失敗した場合、起動失敗状態を記録し、次回のアクセスで再試行できること。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システム MUST 許可された正規業務APIパス（`/api/*`）以外の未定義パス（`/robots.txt`, `/favicon.ico` 等）への要求を受信した際、ルーティングゲート（`Routing Gate`）においてバックエンド処理基盤の起動処理を呼び出さず、即座に 404 Not Found を応答しなければならない。
- **FR-002**: システム MUST 正規業務APIパスへの要求を受信した際、バックエンド処理基盤が停止中であれば起動処理を開始し、クライアントに起動中通知（HTTP 503 Retry-After: 15）を返却しなければならない。
- **FR-003**: システム MUST バックエンド処理基盤の起動要求を受け付けた時点（`record_request_accepted` および `_claim_start` 実行時）で、システム活動状態（`SystemActivity`）の最終活動時刻（`lastActivityAt`）の初期値として現在時刻（ISO8601）を記録しなければならない。
- **FR-004**: システム MUST 初回の起動要求後にクライアントからの後続要求が1件も到着しなかった場合でも、起動要求時刻から規定アイドル時間（7,200秒＝2時間）が経過した後の定期アイドル監視パトロール（`check_and_auto_sleep`）において、バックエンド処理基盤を安全にスリープ状態（タスク数0）へ自動停止しなければならない。
- **FR-005**: システム MUST 定期アイドル監視パトロール（`check_and_auto_sleep`）において、バックエンド処理基盤の実タスクが稼働中であるにもかかわらず活動記録が起動中状態（`runtimeState="STARTING"`）のまま残っている場合、起動ロック期限経過（`startLockExpiresAt <= nowEpoch`）、処理中要求数ゼロ（`inFlightCount == 0`）、および規定アイドル時間経過を確認したうえで停止処理の対象としなければならない。また、万一 `lastActivityAt` が未設定の場合は第1候補 `startRequestedAt`、第2候補 `lastAcceptedAt` の優先順位でフォールバック評価し、両方欠落時は `invalid_runtime_activity` として既存の安全装置（フェイルオープン）に委ねなければならない。
- **FR-006**: システム MUST 自動停止処理の実行中に新たな正規業務要求を受信した場合、世代番号（`generation`）の競合検出により新規要求を優先して起動状態を維持または即座に再起動しなければならない。
- **FR-007**: システム MUST 許可外パスの遮断結果、起動要求の受付、最終活動時刻（`lastActivityAt`）の記録、および自動停止判定の結果を監査ログ（`_log_audit`）に記録しなければならない。（実装対応: `_log_audit` 呼び出しを `record_request_accepted`・`_claim_start`・`check_and_auto_sleep` 修正時に確認・追加すること。対応タスク: T016）

---

### Key Entities *(include if feature involves data)*

- **System Activity (システム活動状態)**:
  - システム全体のバックエンド稼働状態（停止 `STOPPED`、起動中 `STARTING`、稼働中 `RUNNING`、停止処理中 `STOPPING`、起動失敗 `START_FAILED`）。
  - 主要属性: 稼働世代（`generation`）、処理中操作数（`inFlightCount`）、最終受付時刻（`lastAcceptedAt`）、最終活動時刻（`lastActivityAt`）、起動要求時刻（`startRequestedAt`）、起動ロック失効時刻（`startLockExpiresAt`）、停止要求時刻（`stopRequestedAt`）。（定義詳細: [ubiquitous-language.md](../../docs/ubiquitous-language.md) および [data-model.md](./data-model.md)）
- **Routing Gate (ルーティングゲート)**:
  - 受信した要求のパスを検証し、バックエンド処理基盤への転送・起動トリガー対象となる正規業務APIパス（`/api/*`）と、対象外パス（即座に404応答）を振り分けるエントリーポイント。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `/robots.txt`、`/favicon.ico` などの非業務パスに対するアクセスにおいて、100%のケースでバックエンド処理基盤の起動が遮断され、50ms未満で即座に 404 Not Found が返却されること。
- **SC-002**: 起動要求後に後続要求が0件のケース（早期離脱・単発アクセス）において、規定アイドル時間（7,200秒＝2時間）経過後、15分間隔で実行される定期アイドル監視パトロールにより最大15分以内に100%バックエンド処理基盤がスリープ状態（タスク数0）へ自動停止すること。
- **SC-003**: 正規業務API（PC一覧取得、PC登録等）利用時のオンデマンド自動起動および画面操作の応答成功率・可用性が既存同等以上を維持すること。
- **SC-004**: 検索ボットやクローラーのアクセスによる不要なバックエンド稼働時間が月間0分になり、無駄なインフラ課金が完全に排除されること。（本 KPI は FR-001・FR-003・FR-005 の実装（T004, T005, T009, T011）により保証される）

## Assumptions

- フロントエンドからバックエンド処理基盤への正規通信は、すべて `/api/` プレフィックスで始まるパス構成となっている（例: `/api/pcs`, `/api/auth/*`）。
- 非業務パス（`/robots.txt`, `/favicon.ico` 等）へのリクエストは、認証・認可やバックエンド起動処理に入る前のルーティングゲート層（FastAPI ルーティング）で即座に 404 Not Found として応答される。
- アイドル判定基準時間（7,200秒＝2時間）および定期アイドル監視パトロール間隔（15分間隔）の基本ポリシーは既存のコスト最適化設計を踏襲する。
- 業務APIに対する認証・認可および内部要求署名（`Internal Request Signature`）の検証ロジックには変更を加えない。
